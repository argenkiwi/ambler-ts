Same class of bug as the post-rebrand drift note (linked): azk-reference's hand-maintained prose had fallen behind actual node behavior, discoverable only by reading nodes/*.ts, not the CLI's own Usage:/error output.

Two gaps found and fixed:

1. Exit code is not a reliable success signal. CLI-argument validation (missing query/id/fromId, malformed JSON on stdin) calls Deno.exit(1). But failures raised inside a node -- get/update/delete's not-found, link's missing-id, create's write/embed failure -- take an edge mapped to `null` in walks/azk.ts, so the process falls off the end of the ROUTE loop and exits 0 with just a printed `{ error }` on stdout. A caller gating on exit code alone (e.g. shell `&&` chains) would treat these as success.

2. create's `links` array is never validated against existing ids, unlike the standalone `link` subcommand which checks both ids first. A dangling `toId` is stored silently and survives `reindex` too, since reindex trusts each note's own frontmatter links without checking the target exists.

Fix applied both at the source (added JSDoc to azk-create/get/update/delete/link/search factories, matching the docstring style azk-reindex.ts already had) and in azk-reference/SKILL.md (all 3 copies: ~/.claude/skills, ambler-ts .agents/skills/azk-reference, and the azk-install asset template) -- kept the reindex.ts docstring as the bar the other five nodes should have met from the start. Did not change runtime behavior (e.g. adding explicit Deno.exit(1) on error edges) since that's a behavior change outside a pure-documentation ask, and other scripts (like azk-install's own verify step, which chains with `&&`) might incidentally depend on today's exit-0-on-error quirk.
