Moved azk out of ambler-ts into a standalone sibling repo at ~/Code/azk. The old design was one walk (walks/azk.ts) with a ROUTE node dispatching to 7 leaf action nodes, all sharing one artificially-unified State interface. Now each action (search/create/get/update/delete/link/reindex) is its own walk with its own narrow State, node, and spec -- the ROUTE node and unified State are gone entirely.

Key design decision: the global CLI UX (azk <verb> ... as one command) had to be preserved exactly, since ~/.claude/CLAUDE.md and other projects' AGENTS.md depend on it. Solution: a thin cli.ts at the repo root does argv-only routing via plain dynamic import(./walks/<verb>.ts), then calls that module's exported main(argv). Each walk still keeps its own if (import.meta.main) block calling the same main, so every walk is independently runnable too (deno run walks/search.ts query). Rejected alternative: spawning deno run as a subprocess per verb -- doubles startup latency and complicates stdin passthrough for create/update, with no real isolation benefit since all 7 walks are trusted first-party code in one repo. Deliberately used plain ESM import() here, not the defer keyword -- defer is a walk-internal convention for lazily loading node factories inside an ambler() graph; cli.ts sits outside the graph entirely and never touches ambler()/Node/NodeFactory.

Gotcha hit while scoping per-walk deno.json task permissions: every one of the 7 actions needs --allow-write, not just the note-writing ones (create/update/delete/link), because utils/db.ts's open() unconditionally calls Deno.mkdirSync before touching SQLite -- even a pure read like search or get trips a write-permission error on the .azk directory. Confirmed by hitting a NotCapable write-access error on a search-only task scoped to --allow-read --allow-net only.

Utils (config/db/fs/embeddings) were copied as shared infra across all 7 new walks, not duplicated per walk -- they're genuine shared infrastructure (one SQLite schema, one Markdown format, one embedding routine), and duplicating them would create divergent copies of the same format, which is worse coupling than sharing a plain utility module.

Retired the azk-init skill (vendoring azk source into a consumer project) since it directly conflicts with the self-contained-standalone-repo goal; azk-install now points at the azk repo (cli.ts) instead of ambler-ts (walks/azk.ts), and ambler-ts itself was cleaned up (old walk/nodes/utils/specs/skills deleted, deno.json/AGENTS.md/README.md updated) to rely purely on the global install, same as any other project.
